### Особенности, которые необходимо сохранить

- В 704 вопросах есть расхождение answer_order/answer_code (2 318 вариантов).
  Например, question_id `beedce68-fcc8-11ea-8f0f-2016b949cb35`:
  верный answer_id `beedce6c-fcc8-11ea-8f0f-2016b949cb35` имеет порядок 5, код 4.
  Числа не являются взаимозаменяемыми; проверка только по UUID/is_correct.
- У 860 вопросов question_order отличается от question_code.
- В 281 вопросе варианты содержат числовые ссылки на другие варианты;
  в 202 из них также есть расхождение кодов и порядка. Сохранение порядка
  обязательно, включая keep_answer_order=false. Семантику этих ссылок
  нельзя автоматически «исправлять» перестановкой или перенумерацией.
- 26 групп повторяющихся текстов охватывают 60 вопросов. Оставить все UUID,
  варианты и иллюстрации раздельными.
- У question_id `4ed65d27-ea9e-11e9-b4e1-0050569f2c05` нет текста пояснения,
  но есть URL: показывать «Пояснение в источнике» и ссылку.
- 428 ссылок ведут на its.1c.ru, 5 на v8.1c.ru. Страницы не загружались;
  доступность и необходимость подписки не проверены.
- Один вариант содержит обозначение клавиши `<Shift>`. Детектор отметил его
  как потенциальную HTML-разметку: это не доказательство наличия HTML.
  Выводить обычный текст через React, сохраняя переносы; если действительно
  потребуется HTML, отдельно санитизировать разрешённые элементы, не теряя
  буквальные угловые скобки. Не использовать необработанный innerHTML.
- Исходный набор назван «Платформа 8.3 изд. 2 с 22.09.2021»;
  даты обновления вопросов: 27.12.2024–08.10.2026. Это метаданные источника,
  не подтверждение актуальности официальной экзаменационной базы.

Машиночитаемый подробный отчёт с UUID, без текстов вопросов:

будут проверяться на этапе 1: приложения и базы пока нет.

## Предлагаемая схема данных

Отделить банк от личной истории и UI. Сохранять стабильные UUID и исходные поля;
не создавать идентификаторы из текста или номера массива.

| Сущность | Ключ и назначение |
|---|---|
| bank_imports | SHA-256 архива, версия формата, результат импорта |
| sections | section_id, section_order/code/title |
| questions | question_id, section_id, question_order/code, text, explanation/url, исходные признаки/updated_at |
| answers | answer_id, question_id (из вложенного JSON), answer_order/code, text, is_correct |
| question_images | question_id + порядковый номер кадра, приватные пути, хеши, размеры; локально Blob |
| attempts | attempt_id; user_id, question_id, answer_id, is_correct, is_unsure, answered_at UTC, session_id, mode, device_id; append-only |
| study_sessions | session_id, режим, раздел, список question_id, текущий question_id, состояние просмотра/выбора, версия, статус |
| user_question_flags | пользователь + question_id; закладка, пропуск |
| review_state | производный кеш по пользователю/вопросу; пересчёт из истории |
| user_preferences | пользователь, настройки, версия схемы |
| sync_outbox | локальные события с уникальным event_id, статус/число повторов |
| app_members | явное разрешение чтения банка в Supabase на этапе 3 |

IndexedDB версионируется миграциями. В этапе 1 локальный профиль имеет UUID;
при подключении Auth нужен явный перенос владельца с сохранением attempt_id.
Запись попытки и позиции — одна локальная транзакция; очередь синхронизации
добавляется в ту же транзакцию на этапе 3. Импорт банка не трогает попытки.
Повторный импорт по UUID обновляет только банк; ошибки импорта откатывают его
целиком. Ключи/содержимое новой версии сравниваются, конфликтующие изменения
не принимаются молча. Нет каскадного удаления истории при обновлении банка.
Серверный кеш review_state не является источником правды.

## Риски и решения перед реализацией

1. **Изменение «наугад» после ответа против immutable-попыток** (ТЗ 5.7 и 8.1).
   Предлагается отдельный append-only журнал attempt_annotations:
   event_id, attempt_id, is_unsure, changed_at UTC, device_id. Эффективная
   уверенность вычисляется поверх исходной попытки, расписание пересчитывается.
   Смена отметки не является новой попыткой. Это предложение для приёмки плана;
   перезаписывать попытку не будем. Конфликты правок с двух устройств должны
   иметь детерминированное разрешение и сохранение обоих событий.
2. **До облака нет защищённого публичного сервера банка.** В этапе 1 импорт
   через выбор локального ZIP пользователем прямо в IndexedDB; архив не
   включать в public/, src/ или сборку. Запуск только локально; публикация
   с загрузкой банка — после Auth/allowlist этапа 3.
3. **Исходные updated_at без часового пояса.** Сохранять как метаданные источника;
   не приписывать им UTC. Время собственных событий — явное UTC.
4. **Сохранность локальных данных.** Очистка данных браузера удалит IndexedDB;
   до резервных копий и облака это ограничение явно указать в README/UI.
   Никаких сбросов базы ради миграций.
5. **Офлайн с двух устройств.** Объединять попытки по UUID, сессии версионировать;
   при конфликте предлагать восстановление, не перезаписывать молча.
6. **Пробный экзамен.** Результаты отдельно; не включать в планировщик автоматически.
   Перед этапом 4 перепроверить актуальность экзаменационных правил по источнику
   из ТЗ; сейчас внешняя проверка не выполнялась.
